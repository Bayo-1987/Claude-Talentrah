### What changed, and the evidence behind it
Production auth logs only exist from 2026-09-29 17:19Z. In that window (counts only): 36 successful refreshes and **0** `refresh_token_already_used`; on 2026-10-02, **10** `refresh_token_not_found` (HTTP 400, all from the server) at 05, 06, 19 and 20 UTC, and **9** sign-outs (11 in the auth log), every one `POST /auth/v1/logout?scope=global` from the server. Reuse detection is not what logged anyone out.
- **Sign-out is per device.** `signOut()` with no argument is `scope: "global"`: it deleted every session the user had, so signing out on one device failed the next navigation on every other. The header's Sign out is now `scope: "local"`. Settings has an explicit **Sign out of all devices** (`global`) with a confirm step that says what it does. A password set through the reset flow now signs out the user's **other** sessions (`scope: "others"`, keeping this one); before this PR it did nothing of the kind (`updatePasswordAction` only called `updateUser`). Account deletion stays global (ACCT-1, #686). A source scan fails on any `signOut(` in `src` with no explicit scope.
- **`carryCookies(from, to)`** (`src/lib/supabase/carry-cookies.ts`): the seeker gate's redirect was built from scratch and dropped every Set-Cookie of the refreshed response. Measured with the real proxy and @supabase/ssr against a fake token endpoint (`tests/support/fake-gotrue.ts`): a dead session's redirect to `/login` carried 0 cookies, so the dead cookies were retried on every request (the repeated 400s per client in the logs); and a refresh that succeeded followed by a failed `/user` call lost the rotated token. It is now carried, with a source scan that fails on a bare `NextResponse.redirect` in `proxy.ts` (only `adminGate`, which runs before the session is read, is exempt). #686's gate already copies cookies with the same loop; S3-21 swaps to the helper after #686 merges.
- **`updateSession` runs exactly once per request** (pinned for four paths, and zero for `/admin`, which returns before it): a second call rebuilds the response and would drop the first call's cookies.
- **`touchLastActive` can no longer refresh a session after the response is returned.** It used the session-bound client; it now builds its own client holding only the access token `updateSession` just validated (no cookies, no persistence, no auto-refresh). `updateSession` returns that token instead of its client. No migration.
- **`/auth/callback` writes the session cookies onto the redirect it returns** (it relied on Next merging `cookies()` writes into a separate redirect; assumed, never proven). Proven now with the real route, the real ssr client and a PKCE verifier cookie. Found on the way: `next` went unvalidated into `${origin}${next}`, so `next=@evil.example` redirected off the site after a valid sign-in; it now goes through `safeRedirectTo`.
- **A transient `getUser` failure on a protected page** keeps its redirect to `/login`; with the cookies carried, the rotated session is no longer lost.
- **Privacy page** (approved wording, October 3, 2026, that page only): "Job descriptions and job-posting links you submit — job descriptions you paste for Farah to analyze or tailor a resume against and, for employers, links to a careers page or job posting you ask us to import (we fetch that page to read the posting)." The Terms carry no matching "linked job postings" claim (searched `src/app/legal`: the only hit is the privacy line); the Terms are unchanged. Both are on the owner's lawyer list.
