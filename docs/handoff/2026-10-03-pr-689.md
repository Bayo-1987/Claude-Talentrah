### What changed
A friend's signup pays nothing; activation (a base resume saved, or a job applied to) pays the whole reward, 50 credits, once. Migration 0215 redefines `handle_new_user`, `grant_referral_reward` and `check_and_activate_referral`, adds `referrals.reward_withheld_reason` (`cap`, `referrer_deleted`) and the read-only `stuck_signed_up_referrals()`. `/refer` is a public landing page when signed out; its copy comes from one set of constants (`src/lib/referrals/`), and a referral held back by the 10-per-30-days cap says so. The claim and the grant run in their own subtransaction: a referrer's payout failure never fails the friend's save or application. Decisions: `docs/referrals-open-questions.md` #1 and #2. Legacy rows are not backfilled (none exist in production). See the PR body for the user-visible effects, the full dry-run evidence and the list of changed existing assertions.

### The stuck-referral check: what it is and how to run it
`public.stuck_signed_up_referrals()` is read-only, SECURITY DEFINER with `search_path=public`, executable by `service_role` only. It lists referrals still `signed_up` although the friend already meets the activation rule (a base resume, or an application with `applied_at`: the same two conditions `check_and_activate_referral` tests). Columns: `referral_id`, `referrer_id`, `referred_user_id`, `signed_up_at`, `qualifies_by` (`base_resume` or `application`), oldest first. Identifiers only: no email, name or other personal field (pinned by `tests/supabase/migration-0215-shape.test.ts`).

Why it exists: `check_and_activate_referral` now catches every payout error so the friend's own save or application cannot fail, which leaves only a Postgres WARNING; and the retry needs the friend to save or apply again, so a friend who qualifies once and never returns would leave the referral unpaid for good. Normally it returns NO rows (the friend's own save triggers the activation in the same transaction); a row means a grant failed, or the friend qualified before the trigger existed. At the 2026-10-03 dry run it returned 0 rows on production.

How to run it (production reads in a READ ONLY transaction), via the Supabase MCP `execute_sql` or the SQL editor as postgres/service_role:
```sql
begin read only;
select * from public.stuck_signed_up_referrals();
rollback;
```
From code: `admin.rpc("stuck_signed_up_referrals")` with the service-role client. To find the cause, search the Postgres logs for `check_and_activate_referral: referral <id> was not paid and stays signed_up for a retry (SQLSTATE <code>)`.
