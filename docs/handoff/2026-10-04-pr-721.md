### What changed
`updateCompanyProfileAction` (`src/lib/employer/actions.ts`) recomputed `verified` from the work-email domain rule alone and wrote it whenever it differed from the stored value. An organisation verified by an admin's CAC confirmation (`cac_confirmed_at` set, the path for an employer whose email is not at the company domain) evaluates false under that rule on every save, so the next save by any member cleared `verified`. The admin CAC queue excludes rows with `cac_confirmed_at` set, so nothing could put the badge back.

The action now computes `shouldBeVerified = domainRule || organization.cac_confirmed_at !== null` and writes that. `cac_confirmed_at` is read from the organisation row `requireEmployer()` loaded (it is written only by the admin decision action; no client has UPDATE on it), never from the form. Three consequences, each pinned by a test:
- a CAC-confirmed organisation stays verified through a save by a member whose email is not at the claimed domain;
- an organisation with no CAC confirmation behaves as before (domain rule, both directions): this fix is not "never lower verified";
- an organisation that the bug already left CAC-confirmed but unverified is restored by its next save.

Production had no CAC-confirmed organisation when this was found (S1's count), so nothing was hurt and no data repair is needed. This lands before the first CAC approval, as the owner asked.
