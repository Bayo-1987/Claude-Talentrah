### What changed
`persistScoresOrRetryStale` upserts a user's scores in one POST. If a posting was deleted mid-run Postgres answers `23503`, and the recovery asked `job_postings` which of the batch's ids still existed with one `.in("id", ids)`. `.in()` puts every id in the request URL; at the board's real size that URL is over the gateway limit, the lookup is refused ("URI too long"), the function returned `ok:false` and the user's whole batch was lost, while the summary stayed `ok`. The lookup now runs in chunks of 200 (`src/lib/supabase/in-list.ts`, `IN_LIST_BATCH_SIZE`, `chunkInList`; the number already existed separately in `ingest.ts` and `posting-deletion.ts`, which now import it). A batch that fits in one chunk still makes one lookup. A successful recovery logs `[match-score-refresh] recovered`. 200 sits at 54% of the smallest failing URL length measured (372 ids, 14,589 characters). What deletes the posting mid-run was not identified; this fixes what the recovery does about it.
