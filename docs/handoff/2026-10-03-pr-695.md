### What changed
The owner logged in from Mentorship, Scholarships and "Hire through Talentrah" and did not land back on the page. The chain broke in four places.
1. **The public masthead's "Log in" and "Get started for free"** went to a bare `/login` and `/signup`. They now carry the current path (and query, read after hydration so no Suspense boundary is added to the static pages) as `redirectTo`; on `/`, `/login`, `/signup`, the other auth screens and the one-time token pages they stay bare (`returnPathFor`, `authLinkWithReturn` in `src/lib/auth/redirect-to.ts`).
2. **Google and LinkedIn dropped the destination** (the callback URL was hard-coded to `/onboarding`). The login and signup pages now pass `redirectTo` with both provider buttons. **The destination travels in a short-lived cookie** (`tr_post_auth`, HttpOnly, SameSite=Lax, 10 minutes, path `/auth`) that `/auth/callback` validates with `safeRedirectTo`, turns into `/onboarding?next=…` and clears. The URL Supabase is asked to redirect to is byte-identical to the one that already works, so nothing depends on how the project's redirect allow-list treats a longer query string (not readable from here). Cost: an emailed confirmation link opened in another browser loses the destination and lands on plain onboarding, as today. Email signup stashes it for that link; Google One Tap navigates to the page they were on (on `/login` or `/signup`, the page that sent them).
3. **The callback fell back to `/dashboard`** (a placeholder that only redirects to `/jobs`) while everything else said `/jobs`. One constant now, `DEFAULT_AFTER_AUTH_PATH = "/jobs"`, used by the callback, the login and signup pages (for someone already signed in) and onboarding.
4. **S1-51: `/onboarding` passes straight through to any `/employer` path.** An employer account with no resume and no recorded skip, logging in from `/employer`, was shown the seeker's "upload your resume" screen. Chosen over an organisation-membership rule because it also covers a brand-new employer with no organisation (the employer landing's sign-up goes to `/employer/onboarding`).

Every destination goes through `safeRedirectTo`; `https://evil.example`, `//evil.example`, `/\evil.example`, `javascript:`, `evil.example/x`, `@evil.example` and `.evil.example` are pinned on the OAuth action, the callback cookie and email login.

Current behaviour for a seeker with no organisation and no resume logging in from `/employer`: before, the resume prompt, then `/employer`, then `/employer/onboarding`; now the prompt is skipped and they arrive at `/employer/onboarding` directly. The four marketing pages return the visitor to the feature they describe (`FEATURE_FOR_MARKETING_PAGE` in `returnPathFor`; exact match, so any other page returns to itself; the marketing page's own query is not carried over). The destination is reached through `/onboarding` like any other, so a user with no resume sees the resume prompt first; a user who skipped it lands on the feature, where `/tailor` asks for a base resume itself, `/resume-builder` offers its first-resume panel and `/auto-apply` opens its empty queue with its off-state notice. No route needed extra gating.

### Existing assertions changed
The first CI run of this PR failed 28 e2e tests, all from the intended change and none a regression (they were unit-green; only the browser sees the masthead's links): `e2e/masthead-signed-out-mobile.spec.ts` located the masthead's links by an exact `href="/login"` / `href="/signup"`, which are now `…?redirectTo=…` on every page but `/` (matched by path prefix now: 22 tests); `jobs-tracker-public-landing`, `mentorship-public-landing` and `scholarships-public-landing` located "the page's own login CTA" by its `redirectTo` href, which the masthead now also carries (scoped to the main landmark, plus a new assertion that the masthead's own Log in carries the same destination); `signed-out-link-repoints` read `input[name="redirectTo"]` as one field, and the signup page now posts it from three forms (the email form and both provider buttons), so every one of the three must carry it exactly. My own employer case asserted `/onboarding` is never visited; it is passed through (a redirect with no page of its own), so it now asserts every `/onboarding` response is a redirect and the upload prompt never renders.
`tests/auth/callback-cookies.test.ts`: after a refused `next` the callback's default was asserted as `/dashboard`; it is now the shared `DEFAULT_AFTER_AUTH_PATH` (`/jobs`). A deliberate rule change.

### The cookie (the owner asked for these to be proven)
