### What changed
Each CI job starts its own local Supabase stack, which pulls about twelve images in parallel from AWS ECR Public. Anonymous pulls from shared runner IPs are rate limited, and a throttled pull killed the `e2e` job on #689, #696 and #698 (`toomanyrequests: Rate exceeded`, every image refused within a second); each passed on its one rerun. The owner approved option 1, a retry, with no secret and no cache.

`.github/actions/local-supabase/start-supabase.sh` (new) replaces the bare `supabase start` in the composite action. Up to three attempts. A failure is retried only when the output contains the registry's rate-limit text (`toomanyrequests` or `Rate exceeded`): it then runs `supabase stop --no-backup` to clear a half-started stack, waits 30 s before the second attempt and 60 s before the third. Any other failure fails on the first attempt with the CLI's own exit code, with no cleanup and no wait, so a real stack problem is never hidden behind a retry. Three throttled attempts in a row is still a failure and says so. The log names the attempt that succeeded (`succeeded on attempt N of 3`). The action still runs `supabase db reset` and exports the same connection details, and adds no secret.

`tests/ci/supabase-start-retry.test.ts` (10 tests) runs the script against a fake `supabase` on PATH and a recording `sleep`, so it needs no network or Docker. It pins the success path, one and two throttles, both spellings of the throttle, fail-fast on any other error (including after a throttled first attempt), three throttles in a row as a failure, and that the action runs the script, still resets the database and uses no `secrets.`.

### Not done, on purpose
Option 2 (an image cache or a registry mirror) stays unbuilt unless failures continue after this. If it is needed it will need a secret on the repository; the owner is told what to add and where, and nothing is added without his word.
