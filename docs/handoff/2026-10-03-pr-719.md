### What changed
Two loaders read `job_postings` with `select("*")`. They now name their columns, and a test holds the rule for the whole of `src/`.
- `src/lib/jobs/job-columns.ts`: `JOB_DETAIL_COLUMNS` (the public job page, its structured data and its share image: every column except the text-search vector and one internal admin column) and `JOB_EDIT_COLUMNS` (what the employer edit form loads). Each is one string literal, because supabase-js types a result from the literal text of `select(...)`.
- `src/app/(app)/jobs/[id]/job-for-request.ts` and `src/app/employer/jobs/[id]/edit/page.tsx` use them. The structured-data builder's parameter type drops the two columns the page no longer loads; nothing in it read them.
- `tests/rls/org-and-referral-scoping.test.ts`: the bystander's read named no columns and asserted zero rows, which would also pass if the read itself failed. It now names columns and asserts the query returned no error before asserting zero rows.
- `tests/jobs/job-postings-explicit-columns.test.ts` (new): no query that starts at `.from("job_postings")` calls `select("*")` or an empty `select()` (comments are stripped first; the scan asserts it found the queries it is meant to scan); the two lists name only real columns of the generated type, once each; `jobForRequest` passes exactly `JOB_DETAIL_COLUMNS` plus the organisation embed; and the set of files that name the internal column is pinned.
- `e2e/job-page-column-lists.spec.ts` (new): the public job page, its JSON-LD and its share image still load. The employer edit page is opened by `employer.spec.ts` and `assessment-file-stage-before-save.spec.ts`.

### Existing tests touched
Only `tests/rls/org-and-referral-scoping.test.ts`, for the reason above.
