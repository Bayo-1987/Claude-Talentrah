### What changed
Production Supabase now enforces a minimum of 8 characters with lowercase, uppercase and digits, plus leaked-password protection (the owner changed the dashboard; no setting is changed here). The form's own check blocking a weak password does not show the server enforces anything once the form is bypassed, and a refusal from the server used to come back as `error.message` verbatim.
- **One rule list.** `src/lib/auth/password-rules.ts` is the only place a rule is written in words. The checklist, the server action's check (`schemas.ts`: now a message that names exactly what is missing, instead of "Password doesn't meet the requirements below"), the sentences explaining a Supabase refusal (`password-errors.ts`) and the declared dashboard policy (`SUPABASE_PASSWORD_POLICY`, built from the list) all read it.
- **Messages.** A leaked password, a too-short one, each missing character type, the same password as before and a rate limit each get a plain sentence. The length and classes quoted are the SERVER's own (so the words are right at the old minimum of 6 and at 8); only a message with no detail falls back to the app's rule.
- **Server-side tests.** `tests/auth/password-server-enforcement.test.ts` calls `signUpAction` and `updatePasswordAction` directly, as an API client would, through the real supabase-js client against an in-process stand-in for Auth that enforces a policy and refuses in GoTrue's documented shapes (`tests/support/fake-gotrue.ts` gained `/signup`, `PUT /user` and a policy). Each case must come back as the plain sentence, never a raw Supabase string and never a generic failure. A stricter server (minimum 10) is quoted as 10.
- **Drift guards.** `tests/auth/password-shared-definition.test.ts`: replace the list (stricter length, a renamed rule, a new rule) and the checklist, the server check, the Supabase sentences and the declared policy all follow; and no user-facing string outside the list may name a rule, so a consumer that bypasses it fails. `tests/auth/weak-password-messages.test.ts` keeps the pin against `supabase/config.toml` (its minimum length is 8; requirements stay `""` locally because CI creates fixture users through the admin API with generated passwords).
- **Checklist redesign** (`password-requirements.tsx`). A rule not yet met was a faint dot. Now: met is a green check; not met is a cross (a different shape) with normal-weight text; each row reads "Met: …" / "Not met: …" to a screen reader (the icons are decorative); both states take identical room so the list does not jump while typing; every marker and text is at least 4.5:1 on paper, card and paper-alt (computed from the real tokens by `tests/support/contrast.ts`).

### Existing tests touched

Same intent (a failed submission re-renders and keeps Country and Terms).
- Nothing else existing changed. `tests/auth/weak-password-messages.test.ts` is new in this PR (opened earlier in the same branch).

### Follow-ups
- The app has no change-password form: the only path that sets a password for a signed-in user is the reset form (`updatePasswordAction`), which sends only the new password. Whether Supabase's "require current password when updating" setting applies to a recovery session is not stated in its documentation, so it should not be enabled until a Settings form that sends `current_password` exists and the reset flow has been checked against it on a non-production project.
- Leaked-password protection is documented by Supabase as available on the Pro plan and above; the leaked-password sentence only fires if it is enabled.
