# Resume PDF text-extraction probe

A record of how the resume documents' PDF text was measured against several text extractors, kept so the
measurement can be **reproduced and audited after the throwaway probe branch and CI artifacts are gone**. It is a
record of a measurement, not of a decision: what to do about the findings is tracked elsewhere.

## What is in this directory

| file | what it is |
|---|---|
| `results-faces.csv` | 780 rows: 65 templates × 3 personas × 4 faces. One row per rendered PDF. |
| `results-wordspacing.csv` | 1,365 rows: 65 templates × 3 personas × 7 variants (a control + 6 `word-spacing` settings). Has two extra columns, `pages` and `ws`. |
| `stage2-faces.log`, `stage2-wordspacing.log` | The full stage-2 output of each run: tool versions (`VER`), per-render rows (`ROW`), aggregates (`AGG`), page-count and word-spacing summaries (`PAGES`, `WSVALUES`, `TOPDAMAGED`). |
| `source/zz-diag-font-extraction.spec.ts.txt` | Stage 1: renders every template and saves the PDF. `DUMP …` tests = the faces run, `WSPROBE …` tests = the word-spacing run. |
| `source/zz-extract-all.py` | Stage 2: runs every extractor over the saved PDFs and counts damaged words. |
| `source/font-probe-*.tsx.txt` | The three throwaway dev routes the probe rendered through (`/dev/font-probe/…`). |
| `source/probe-ci-workflow.patch` | The `.github/workflows/ci.yml` changes the probe ran under (install the extractors, run both stages, upload results). |

The TypeScript sources are stored as `.txt` **on purpose**: a `.ts`/`.tsx` file under `docs/` would be picked up by
`tsc` and ESLint and fail on its `@/…` and `./support/…` imports. Rename them (drop `.txt`) to use them.

**The rendered PDFs are not committed** (they total ~86 MB for the faces run and this is a public repository); they
are regenerated by stage 1.

## What was rendered

- **Templates:** every slug from `registeredSlugs()` (`src/components/resume-builder/templates/index.tsx`) — 65.
- **Personas:** `EXAMPLE_PERSONAS[0]`, `[1]`, `[2]` from `src/lib/resume-builder/preview-sample.ts` (product manager, EPC site
  engineer, development programme officer). `EXAMPLE_PERSONAS` has 66 entries on `main`; **3 of 66 were used.**
  These personas are **fictional** and already live in this repository.
- **Faces (faces run):** `source-sans` (the resume font as it is, no override), `plex`, `work-sans`, `newsreader`. For the
  last three a `!important` `font-family` override was injected on the resume root and its descendants after confirming
  the face was computed and loaded before printing.
- **Variants (word-spacing run):** the face is untouched (Source Sans 3). `ss-ws0` is a no-op control; `ss-ws-each-<X>` sets
  `word-spacing: <X>` on the resume root *and every descendant* (so `em` resolves per element); `ss-ws-root-<X>` sets it on
  the resume root only (descendants inherit the absolute length computed there). `X` ∈ {0.02em, 0.05em, 0.1em}.
- **`ats_safe`:** stage 2 hard-codes the 38 slugs that production had `resume_templates.ats_safe = true` on 2026-09-30.

## How "damaged" is counted

For each rendered PDF:

1. **Body words.** The text of every leaf element under the resume root (`[class*='bg-resume-paper']`), **excluding** elements
   whose computed `text-transform` is `uppercase` or whose `letter-spacing` is over 0.2px (headings are tracked and
   uppercase, so their extraction is a separate question). Non-ASCII characters are replaced with spaces. The words are the
   **unique** alphabetic tokens of **3+ letters** (`/[A-Za-z]{3,}/g`). Mean 135 words per render (min 98, max 170).
2. **Damaged.** A word is damaged if it does **not** appear **as a whole word, case-insensitively** in the extractor's output:
   `(^|[^A-Za-z])WORD([^A-Za-z]|$)`. Words glued together (`Seniorproduct`) or split apart (`Sen ior`) both count as damaged.
3. **Percentages** in the write-ups are `sum(damaged) / sum(words)` over the stated set of renders (all three personas
   unless stated) — words-weighted, not an average of per-render percentages.

What this does **not** measure: whether a given applicant tracking system would still index a damaged word, and reading
order (that is what `e2e/ats-safety.spec.ts` checks, with pdf.js only).

### CSV columns

`persona` (index into `EXAMPLE_PERSONAS`), `face` (face id or word-spacing variant id), `slug`, `words` (body words checked),
`pdfjs` / `poppler` / `pdfminer` / `mutool` / `pdfbox` (damaged-word count for that extractor), `fams` (the computed font
families of the text, `|`-separated), and in `results-wordspacing.csv` also `pages` (page count) and `ws` (the distinct
computed `word-spacing` values on the text, `|`-separated).

### The CSVs contain no resume text

Both files were checked cell by cell: every `persona`, `words`, extractor and `pages` cell is an integer; every `slug` is a
kebab-case template id; every `face` is an id; `fams` holds only font-family names (`Source Sans 3`, `IBM Plex Sans`,
`Work Sans`, `Newsreader`, `Lora`, `Poppins`, `Barlow Condensed`); `ws` holds only lengths such as `0.8px`. **Neither CSV
contains any words from a resume, fictional or otherwise.** The `.log` files do quote a few damaged words (for example the
most frequently damaged ones); those words come from the fictional example personas above, which are already in the repository.

## Headline numbers (so the CSVs are easy to sanity-check)

Percent of body words damaged, Source Sans 3 as it is today, all 65 templates × 3 personas (195 renders):

| extractor | damaged / total | % |
|---|---|---|
| pdf.js | 180 / 26,384 | 0.68% |
| poppler | 7,816 / 26,384 | 29.62% |
| pdfminer.six | 194 / 26,384 | 0.74% |
| MuPDF | 0 / 26,384 | 0.00% |
| PDFBox | 233 / 26,384 | 0.88% |

Poppler under a small `word-spacing` (the four other extractors are identical to the control render-by-render in every
variant): `each 0.05em` 0.90%, `root 0.05em` 0.56%, `0.1em` 0.00%, `0.02em` 12.5–18.2%. At 0.05em the page count rises in 11 of
195 renders; at 0.1em in 12 (each) or 21 (root).

## Reproducing

On Linux with `poppler-utils`, `mupdf-tools`, a JDK, `pdfminer.six` and the PDFBox app jar installed
(`source/probe-ci-workflow.patch` shows the exact CI steps):

1. Check out commit `352cd0c7` (`git fetch origin pull/573/head`), or apply the `.txt` sources here to a checkout.
2. `npm ci && npm run build && npm run start`.
3. Stage 1 — `E2E_BASE_URL=http://localhost:3000 npx playwright test e2e/zz-diag-font-extraction.spec.ts -g DUMP --workers=4`
   (faces) or `-g WSPROBE --workers=4` (word-spacing). PDFs and sidecar JSON are written to `/tmp/pdfs`.
4. Stage 2 — `PDFBOX_JAR=/path/to/pdfbox-app.jar python3 scripts/zz-extract-all.py /tmp/pdfs`; it prints the `VER`/`ROW`/`AGG`
   lines and writes `/tmp/pdfs/results.csv`.

## Known limits of this measurement

- **Linux Chromium only.** PDFs produced on macOS, Windows or Android were not measured (beyond one early pdf.js-only macOS
  check). Poppler on non-Linux PDFs is untested.
- **Five open-source extractors.** No commercial parser and no real applicant tracking system was run.
- **Three of 66 personas.** Damage scales with the words a template contains.
- **The mechanism is not established:** these files show *that* poppler reports no word gaps in the current PDFs and *that* a
  larger `word-spacing` removes the effect, not *why*.
- The word-spacing run kept only first-page PNGs of two templates, not the PDFs, so how the spacing looks at proper resolution
  was not reviewed.
